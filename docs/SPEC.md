# school-helper — спецификация MVP

Telegram-бот и Mini App для родительского комитета одного класса.

**Класс:** 1 «В», школа №101 · **Валюта:** сум (UZS) · **Часовой пояс:** Asia/Tashkent

---

## 1. Принципы

Три правила, из которых выводится всё остальное.

### 1.1. Родитель не открывает приложение

В классе из 24 родителей активны 3–5 (комитет), остальные читают чат по диагонали. Поэтому:

> Всё, что требуется от обычного родителя, делается **кнопкой под сообщением бота**.
> Mini App — рабочее место комитета и витрина отчётности для тех, кто захотел посмотреть.

Следствие: разработка идёт **бот → Mini App**, а не наоборот.

### 1.2. Telegram — поговорить, school-helper — зафиксировать

Приложение не заменяет чат и не конкурирует с ним. Оно фиксирует результат: что решили, кто сколько внёс, куда потратили.

### 1.3. Прозрачность важнее функций

Главный конфликт родительских комитетов — недоверие к деньгам. Убийственная фича продукта — не голосования и не календарь, а **постоянно доступный отчёт «поступило / потрачено / остаток» с чеками и подтверждением второго человека**.

---

## 2. Правовая и этическая рамка

Сборы денег в школе — юридически чувствительная тема, а аккуратно зафиксированный список «кто не сдал» может сыграть против класса. Требования к дизайну, обязательные к соблюдению:

1. **Никогда не показывать публично, кто не платил.** Ни списком, ни в виде «17 из 24» — в классе на 24 человека семеро вычисляются за минуту. В группе — только сумма и прогресс-бар.
2. **Поимённый список видит узкий круг**: казначей, председатель, ревизор. Родители предупреждаются об этом при онбординге.
3. **Все взносы добровольные.** Возможны частичная оплата и освобождение (`waived`) — тихое, без статуса «должник».
4. **Минимум персональных данных.** Имя родителя + имя ребёнка (без фамилии). Телефоны, адреса, медицинские данные — не хранятся.
5. **Учитель не имеет доступа к денежному контуру вообще** — см. 3.2.
6. **Годовое удаление.** Конец учебного года → экспорт архива → удаление персональных данных.

### 3.2. Учитель вне денег

Педагог не должен фигурировать в денежном контуре даже как наблюдатель. Это защищает и его, и комитет. Учитель живёт только в расписании и объявлениях.

### 3.3. Правило двух рук

Расход создаёт казначей — утверждает председатель или ревизор. Никто не проводит расход в одиночку. Расходы до `EXPENSE_AUTO_APPROVE_UZS` (по умолчанию 100 000) утверждаются автоматически, чтобы мелочёвка не парализовала процесс.

### 3.4. Передача полномочий

Роли хранятся в `person_role` с историей (`granted_at` / `revoked_at`). Смена председателя — новая запись, а не UPDATE.

## 4. Модель данных

### 4.1. Центральная идея: Событие

**Событие** (`event_case`) — длящееся дело со стадиями:

```
идея → голосование → сбор денег → расходы → закрытие → хроника
```

Голосования, сборы, расходы и календарные даты привязываются к Событию. Отсюда:

- «Хроника класса» получается бесплатно — это закрытые События по датам;
- у каждого События готовый итог: собрано / потрачено / остаток, чеки, протокол голосования;
- вопрос «куда делись деньги за цирк?» через год решается одной ссылкой.

### 4.2. Четыре разные сущности, которые легко спутать

| | что это | пример |
|---|---|---|
| `event_case` | длящееся дело со стадиями | «Поездка в цирк» |
| `calendar_event` | точка во времени | «12 сент, 18:00 — собрание» |
| `announcement` | объявление учителя | «Завтра сокращённый день» |
| `lesson_slot` | расписание уроков | «Пн, 3-й — математика, каб. 205» |

Событие может порождать календарные точки; календарная точка может жить сама по себе.

### 4.3. СУБД

SQLite + WAL. На 24 человека (и на сотни классов при таком темпе записи) Postgres — лишняя операционная нагрузка; бэкап здесь = копирование одного файла, что для денежных данных ценнее масштабируемости. Схема портируемая.

Полный DDL: [`src/schoolhelper/storage/schema.sql`](../src/schoolhelper/storage/schema.sql).

### 4.4. Денежные инварианты

- Все суммы — **целые числа в сумах**. Никаких float.
- Остаток кассы = `SUM(in) − SUM(out)` по неотсторнированным строкам `ledger_entry`. **Баланс никогда не хранится полем.**
- `ledger_entry` неизменяем. Правок нет — есть сторно (`reverses_id`).
- Каждая денежная мутация пишет `audit_log` и `case_entry`.

### 4.5. Мультиклассовость

`class_id` присутствует во всех таблицах с первого дня. Стоит сейчас ничего, стоит дорого потом. Админки классов в MVP нет — один класс заводится сидом.

## 5. Ключевые механики

### 5.1. Сверка платежей

Реальность казначея — 24 перевода на личную карту и пуши от банка. Ручное сопоставление «кто перевёл 50 000 в 23:41» и есть работа, которую нужно снять:

1. У каждого сбора есть `payment_code` (`1V-NG`), родитель указывает его в комментарии перевода.
2. Казначей пересылает боту SMS/пуш банка — бот парсит сумму, время, код.
3. Экран «Не опознано»: непривязанные поступления рядом с неоплаченными взносами, матчинг в один тап.

### 5.2. Анонимные голосования

В группе из 24 знакомых людей открытое голосование по деньгам смещает результат — «против» не голосует никто. Для денежных вопросов анонимность по умолчанию.

Реализация: `vote.person_id = NULL`, `vote.voter_hash = HMAC(secret, poll_id || person_id)` — защита от двойного голоса без раскрытия личности.

### 5.3. Кворум и дедлайн

По истечении `deadline_at` бот закрывает голосование, непроголосовавшие фиксируются как «воздержались» **явно** в `poll.result` — иначе итог «19 из 24» потом оспорят.

### 5.4. Асимметрия видимости

| | кто видит поимённо |
|---|---|
| Кто не сдал деньги | только money-роли |
| Кто не прочитал объявление | **учитель** (ей надо позвонить), родителям — счётчик |

Правило разное, потому что разная цена ошибки.

### 5.5. Оффлайн-родители

Часть родителей не в Telegram или просто ничего не нажмёт. `person.tg_user_id = NULL` — казначей ведёт их вручную (`payment.entered_by`).

`person.dm_open` — нажал ли человек Start в личке. Пока `0`, бот **не может написать первым**. Система показывает: «7 родителей не подключили бота — они не получат напоминания».

### 5.6. Хранение файлов

Чеки и фото хранятся в Telegram по `file_id` — бесплатно, без S3 и бэкапов. Ограничение: `file_id` живёт, пока жив бот; при смене токена ссылки теряются. Раз в год — выгрузка архива.

### 5.7. Очередь уведомлений

Отправка только через таблицу `notification`, не напрямую. Причины: лимиты Telegram (429), заблокировавшие бота, ретраи. Иначе одна ошибка ломает рассылку по всему классу.

**Антиспам:** напоминание о взносе — максимум дважды (за 3 дня до дедлайна и в день дедлайна), только в личку, только тем, у кого `status != confirmed` и `waived = 0`.

## 6. Сценарии бота

### 6.1. Онбординг

Председатель в группе: `/setup` → бот публикует сообщение с кнопкой, ведущей на
`t.me/<bot>?start=join_<class_id>_<hmac>`.

Подпись не даёт подделать ссылку, но не мешает её переслать. Поэтому пришедший
по ссылке **ждёт одобрения председателя**: до него он не видит кассу, не получает
рассылок и не участвует в сборах. Председателю приходит карточка заявки с
кнопками «Впустить / Отклонить»; то же — во вкладке «Люди». Впущенный попадает
и в уже идущие сборы. Исключённый или отклонённый может подать заявку снова —
снова через одобрение.

В личке бот спрашивает имя (подставляя из профиля) и имя ребёнка, затем **прямо говорит**:

> Информацию о ваших взносах видят казначей и председатель. Остальным родителям она не показывается.

Это снимает половину будущих вопросов.

### 6.2. Сбор денег

Казначей создаёт сбор → бот публикует в группу:

```
💰 Новый сбор: Подарки на Новый год
По 50 000 сум · до 15 декабря
При переводе укажите код: 1V-NG

Карта: 8600 **** **** 1234 (Мария К.)

[ Я оплатил ]   [ Подробнее ]
```

`Я оплатил` → запрос скрина → `payment(status='claimed')` → казначею:

```
🧾 Анна И. заявила оплату 50 000
[фото чека]
[ ✅ Подтвердить ]  [ ❌ Не вижу платежа ]
```

Подтверждение пишет `ledger_entry` + `case_entry` и редактирует закреплённое сообщение в группе:

```
💰 Подарки на Новый год
███████████░░░░ 850 000 / 1 200 000
```

Прогресс без имён и без «17 из 24».

### 6.3. Голосование

Inline-кнопки в группе, сообщение редактируется после каждого голоса:

```
🗳 Едем в цирк 2 ноября?
Билет ~45 000 с человека
Голосование анонимное, до 18 окт, 20:00

[ 🔵 Да (12) ]  [ ⚪ Нет (2) ]  [ 🟡 Своё мнение → ]

Проголосовали: 14 из 24
```

Mini App нужен только для «Своё мнение» и сложных голосований (выбор даты сеткой).

### 6.4. Объявления учителя

Два пути:

- **Учитель пользуется ботом** — пишет в личку, бот спрашивает важность.
- **Учитель не пользуется (вероятнее)** — пишет обычным сообщением в группу, председатель делает реплай `/объявление`, бот оформляет с `on_behalf_of`. Нулевое трение.

Для `urgent` + `require_ack` — личка каждому с кнопкой `✅ Прочитал`; учителю экран «кто не прочитал» поимённо.

### 6.5. Расписание

Pull-модель, без спама: `/сегодня`, `/завтра`, `/расписание`.

```
📚 Завтра, пятница 19 сентября

⚠️ Сокращённый день — до 12:00

1. 08:30  Математика       каб. 205
2. 09:25  Родной язык      каб. 205
3. 10:20  ❌ Физкультура — отменена
4. 11:15  Рисование        каб. 118
          🎨 принести цветную бумагу
```

Строка «принести» подтягивается из `calendar_event(kind='bring')` на эту дату.

При создании `timetable_override` бот **автоматически** публикует изменение в группу — это замена еженедельному вопросу «а завтра со скольки?».

## 7. Экраны Mini App

Нижнее меню — 4 вкладки: `🏠 Главная`, `💰 Деньги`, `📚 Расписание`, `☰ Ещё`.

### 7.1. Главная — лента действий, не сетка иконок

Сетка иконок заставляет думать «куда идти». Лента отвечает на вопрос «что от меня нужно прямо сейчас»:

```
ЧТО ОТ МЕНЯ ЖДУТ
  💰 Взнос 50 000 до 15 дек      [ Оплатить ]
  🗳 Едем в цирк? до 18 окт      [ Голосовать ]
  🎨 Завтра: цветная бумага

🔴 ОБЪЯВЛЕНИЕ
  Завтра занятия до 12:00              [ ✅ Ок ]

📚 Завтра: 4 урока, с 08:30
💰 Касса класса: 1 250 000  →
```

Если не требуется ничего — «Всё в порядке, от вас сейчас ничего не нужно». Это тоже информация.

### 7.2. Деньги — два разных экрана по роли

**Родителю** — прозрачность: остаток, обороты, последние расходы (каждый раскрывается: чек, кто платил, кто утвердил, к какому Событию), свои взносы.

**Казначею** — рабочее место: очередь на подтверждение, непривязанные поступления, разрез сбора (подтверждено / заявлено / не платили + кнопка «напомнить»).

### 7.3. Событие и Хроника

```
┌──────────────────────────────────────────────────────────┐
│  🎪 Поездка в цирк                          ЗАКРЫТО      │
│  12 октября — 3 ноября 2026                              │
├──────────────────────────────────────────────────────────┤
│  12 окт  📌 Открыто · Анна                               │
│  13 окт  🗳 Голосование: едем?                           │
│  15 окт  ✅ Решено: едем — 19 за, 2 против, 3 возд.      │
│  19 окт  💰 Сбор открыт — 45 000 × 22                    │
│  28 окт  💰 Сбор закрыт — 990 000 из 990 000             │
│  30 окт  🧾 Расход: билеты 880 000 🧷 чек                │
│          Утвердил: Сергей (председатель)                 │
│   2 ноя  📷 12 фото                                      │
│   3 ноя  🔒 Закрыто · «Остаток 10 000 в кассу класса»    │
├──────────────────────────────────────────────────────────┤
│  Собрано 990 000 · Потрачено 980 000 · Остаток 10 000    │
└──────────────────────────────────────────────────────────┘
```

Хроника — список закрытых Событий по месяцам с итогами. Годовая граница: в конце учебного года класс «закрывает книгу», остаток переносится строкой `ledger_entry(source_type='carryover')`.

**`case_entry` пишется автоматически** из всех модулей, которые меняют состояние. Ручное ведение хроники умрёт на второй месяц.

## 8. Архитектура

Один процесс: **FastAPI + aiogram 3**. Вебхук Telegram приходит в тот же FastAPI, статика Mini App отдаётся с того же домена → никакого CORS, один контейнер, Caddy спереди.

```
Caddy ──► uvicorn ──┬── POST /tg/webhook/<secret>   (aiogram)
                    ├── /api/*                      (FastAPI)
                    └── /                           (статика Mini App)
                            │
                        SQLite (WAL)
```

Dev-режим — long polling (`python -m schoolhelper.runner`), прод — вебхук.

### 8.1. API

```
POST /tg/webhook/<secret>          вебхук Telegram

GET  /api/me                        профиль + роли + класс
GET  /api/home                      лента «что от меня ждут»

GET  /api/cases?status=done         хроника
GET  /api/cases/{id}                событие + case_entry[]
POST /api/cases                     создать              (chair)
POST /api/cases/{id}/close          закрыть + outcome    (chair)

GET  /api/money/summary             остаток, обороты     (кроме teacher)
GET  /api/money/ledger              журнал
GET  /api/collections/{id}          поимённо — только money-роли
POST /api/collections               создать              (treasurer|chair)
POST /api/payments                  заявить оплату       (о себе)
POST /api/payments/{id}/confirm     подтвердить          (treasurer)
POST /api/expenses                  создать              (treasurer|chair)
POST /api/expenses/{id}/approve     утвердить            (chair|auditor)
GET  /api/money/unmatched           непривязанные        (treasurer)

GET  /api/polls/{id}
POST /api/polls                     создать              (treasurer|chair)
POST /api/polls/{id}/vote

GET  /api/timetable?date=           расписание + overrides
PUT  /api/timetable/version/{id}    (teacher|chair)
POST /api/timetable/override        (teacher|chair)

GET  /api/announcements
POST /api/announcements             (teacher|chair)
POST /api/announcements/{id}/ack
GET  /api/announcements/{id}/acks   учителю поимённо, остальным счётчик

GET  /api/calendar?from=&to=
GET  /api/audit                     (chair|auditor)
GET  /api/export/report.xlsx
```

Любой POST, меняющий деньги, принимает `Idempotency-Key` — двойной тап в метро не должен создавать два платежа.

## 9. Безопасность

Три вещи, без которых нельзя запускать.

**1. Валидация `initData`** (`core/security.py`):

```
secret = HMAC-SHA256(key="WebAppData", msg=BOT_TOKEN)
check  = HMAC-SHA256(key=secret, msg=data_check_string)
```
сверить с `hash`, затем проверить свежесть `auth_date` (≤ 24 ч).

**2. Роль — только из БД, никогда с клиента.** С клиента приходит исключительно `tg_user_id` из проверенного `initData`; кто ты и что можешь — резолвится на сервере по `person_role`. Подделать запрос из браузера — дело пяти минут, и голосование по деньгам первая мишень.

**3. `class_id` из сессии, не из параметров.** Иначе при появлении второго класса первый же любопытный прочитает чужую кассу.

Плюс: rate-limit на `POST /api/payments`, все денежные мутации в `audit_log`, сторно вместо UPDATE/DELETE в `ledger_entry`.

## 10. Этапы

| Этап | Содержание | Оценка |
|---|---|---|
| **1** | **Только бот.** Онбординг, сбор денег кнопками, подтверждение казначеем, голосования inline, отчёт `/касса` текстом | ~2 недели |
| **2** | **Mini App: деньги и события.** Касса, рабочее место казначея со сверкой, страница События, хроника | ~2–3 недели |
| **3** | **Школьный контур.** Расписание с заменами, объявления, календарь, напоминания | ~1–2 недели |
| **4** | По результатам: задачи, документы, экспорт, годовое закрытие | — |

Схема БД делается сразу целиком — она дешёвая. Код — по этапам.

**Критерий после этапа 1:** если через месяц не пользуются — дальше не идём. Потеряны две недели, а не три месяца.

**Метрики успеха** — не DAU, а:
- за сколько дней собираются деньги (было ~2 недели → цель 3 дня);
- сколько раз в чате спросили «а сколько сдавать / куда делись деньги» (цель — ноль).

## 11. Принятые решения и допущения

- **Учительница, скорее всего, ботом пользоваться не станет.** Основной путь для объявлений и расписания — через председателя с `on_behalf_of`; прямой вход учителя опционален.
- **Платежей через Telegram Payments не будет.** Провайдеры (включая Payme/Click/Uzum) требуют мерчант-аккаунт юрлица; Stars для сборов между физлицами не подходят. Схема «реквизиты + скрин + подтверждение казначея» — не временный костыль, а постоянное решение.
- **Из MVP исключены**: документы, карточки родителей, раздел «Школа», задачи. Они хорошо выглядят на макете и не используются.
